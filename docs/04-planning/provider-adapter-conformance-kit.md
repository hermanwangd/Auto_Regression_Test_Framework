# Provider Adapter Conformance Kit

The built-in v0.3 provider gate compares the public catalog, the production dispatcher and successful operations observed in actual suite results. The normal Maven verification runs its portable JUnit cases. Linux Framework Gates then exercises six providers against isolated native services or host processes and requires a receipt for every public contract. [JUnit kit](../../src/test/java/com/specdriven/regression/contract/v03/ProviderConformanceTest.java) · [Registrations](../../src/test/resources/provider-conformance.json) · [CI gate](../../scripts/ci/provider-conformance.py) · [Workflow](../../.github/workflows/ci.yml)

## What counts as executable

The support registry contains 26 provider types across versions. There are 18 supported types, five contract-only types, two deprecated types and one unsupported type. The 20 typed v0.3 contracts contain 62 operation declarations. **The 18 supported contracts declare 58 pairs. Of these, 56 execute and two reserve explicit mock startup.** CI derives the expected inventory from the YAML and checks the implementation's actual registrations. Adding a supported type, operation or dispatched adapter without a corresponding fixture fails the gate. [Typed catalog](../02-architecture/contracts/provider-contracts/) · [Status registry](../02-architecture/contracts/provider_capability_registry.v0.2.yaml) · [Runtime dispatch](../../src/main/java/com/specdriven/regression/contract/v03/V03RuntimeExecutionService.java)

| Route | Contracts / executable pairs | Included contracts |
| --- | --- | --- |
| Portable provider execution | 10 / 28 | `grpc_client`, `grpc_mock`, `http_mock`, `ibm_mq`, `jdbc`, `kafka`, `nats`, `polling_observer`, `rest_client`, `soap_mock`. These use the registered profile, including real loopback mock servers, mock brokers, H2 or the file-based observer. |
| Framework assertions | 2 / 6 | `artifact_compare` and `common_verify` each evaluate `json_match`, `schema_match` and `file_diff`. The gate reads the assertion verdict and evidence and checks that provider dispatch stayed idle. |
| Native packaged CLI | 6 / 22 | `cli_process` runs Node/Playwright, `mongodb` uses MongoDB, `redis` uses Redis, `s3` uses versioned MinIO, `sftp` uses OpenSSH, and `websocket` uses a loopback application and a real WebSocket session. |

The `start_grpc_mock` and `start_soap_mock` declarations carry `execution_status: contract_only` and a reason. Loading the first stub starts the managed service. The kit requires the adapter to deny explicit startup while the declaration remains reserved. The reviewed-only `grpc_descriptor_admission` has a runtime class but refuses ordinary dispatch. The unsupported `sample_fake_provider` serves the golden framework fixture. Neither produces public conformance receipts. The full build covers IBM MQ; the `no-ibm-mq` build checks denial before execution. ## Adding a provider or operation

1. Declare its support status, typed operation, legal phases, modes, bindings, inputs, outputs and failure codes in the source catalog. For a reserved operation, state its reason and keep ordinary dispatch blocked.
2. Add one fixture record in `src/test/resources/provider-conformance.json`. Its fields are `contract`, `proof` (`portable`, `assertions` or `native`), `suite` (relative to the P0 samples), `operations` and `boundaryTest` (an executable Surefire class and method). Reuse an existing suite when one workflow covers several operations. Add a provider-specific failure or boundary assertion that can detect incorrect behavior.
3. Exercise each declared executable operation in its normal phase and check its observable effect. For the portable lane, the kit runs a working copy of the sample and reads actual provider steps and outputs or actual assertion verdicts. Additional checks in the copy exercise operations missing from the usage example. For a native lane, call `scripts/ci/provider-conformance.py <contract> <fresh-result.json> ...` after verifying CLI evidence and independent service state. Only successful steps for the matching target and native provider count toward native operation coverage. For a registered native outage, also supply `--outage-result` from the failed scenario.
4. Run the portable gate with `MAVEN_OPTS="-Xmx768m" ./mvnw -Dtest=ProviderConformanceTest test`. Native scenarios run in their existing CI steps. The concluding `--complete` gate checks the public fixtures, JUnit boundary outcomes and receipts against the SHA, job run and attempt. CI retains `target/provider-conformance/{portable,native}/<contract>.json` and the Surefire reports in the framework verification artifact. A required missing, skipped or failed boundary case prevents completion.

## Minimum behavior and evidence

| Requirement | Executable check and applicability |
| --- | --- |
| 1. Contract, operation and runtime mode | The kit probes each registered adapter with every admitted operation, a foreign contract and an unknown operation. An invalid mode must fail through the ordinary suite/compiler path. Framework verifiers follow their assertion path. |
| 2. Invalid or additional input before provider I/O | Each dispatched type gets an undeclared input in its sample and must fail preflight before provider execution. Direct tests add stronger observations where available, including MongoDB invalid criteria before client creation, Redis invalid commands, and REST rejection before HTTP or evidence creation. Framework assertions have their own typed validator. |
| 3. Runner-owned bindings | Every fixture rejects a foreign binding key. Providers with fixed runner binding identities also exercise substitution or tamper rejection, including Redis URI, MongoDB URI, SFTP private key and CLI executable pin. Generated mock endpoints and contract-permitted profile bindings retain their declared meaning. |
| 4. Bounded work | The gate requires actual tests for child process time and output, MongoDB document size, S3 transfer size, SFTP file size, WebSocket event count, gRPC deadline and polling timeout. The verifier fixtures use the JSON/schema work budgets. Bounds apply to the operation's resource. A file-based assertion has no socket lifetime. |
| 5. Evidence redaction | The runner test injects sensitive outputs and provider evidence. Provider probes exercise secret-like CLI output, echoed HTTP JSON, Redis credentials, MongoDB driver failures and S3 service errors. Portable results resolve evidence within their run directory. Native scripts run packaged `validate-evidence`. |
| 6. Stable failure classification | Output validation rejects failure codes absent from the contract. Exact-code cases include MongoDB document mismatch, a failed native JDBC connection, IBM MQ connection failure, polling timeout and S3 false delete acknowledgement. Each contract also has a required boundary test whose Surefire report must show execution. |
| 7. Cleanup and end of run | The kit verifies HTTP, SOAP and gRPC listener closure after a failed suite omits cleanup. Sequential cases reuse the same fixed port after the preceding case finishes, including following a failed assertion. Ending a case closes its targets while listeners owned by other cases or runs remain reachable. CLI interruption verifies child cleanup and recovery. Native WebSocket observes close handshakes, and store/transfer fixtures verify owned resource cleanup independently. Stateless assertions have no provider session to end. |
| 8. Outage, primary failure and cleanup failure | Native MongoDB and Redis each produce a failed post-write read and separate failed cleanup. Native S3 produces a failed post-write verification and a successful cleanup. The gate reads the primary classification, step and separate cleanup failures from the actual case result. Ordinary JDBC also has a regression for primary failure plus cleanup error. A receive-only check without a cleanup action cannot produce an independent cleanup failure. |
| 9. Public status | The catalog/dispatcher test checks the entire production registration set and cross-checks support status, assertion-only execution, reserved operations, reviewed admission and the internal fixture. Registering the latter two as public executable would fail. |

The portable and native receipts describe the environment actually exercised. For example, portable Kafka confirms its mock-broker case, and packaged MinIO confirms S3-compatible behavior in that implementation. These receipts do not establish caller-owned environment acceptance. [Public support matrix](../09-operations/provider_support_matrix.md)

## Two recovery cases with different outcomes

**MongoDB.** The native script observes an acknowledged seed, closes the runner's subsequent read and cleanup connections, verifies `MONGO_OPERATION_FAILED` for both operations, and inspects the recovered document and untouched control with `mongosh`. Recovery deletes only the matching document ID and owner. The injection point is after write acknowledgement. [Native fixture](../../scripts/ci/verify-native-datastores.sh) · [Driver-level tests](../../src/test/java/com/specdriven/regression/contract/v03/adapter/MongoV03AdapterTest.java)

**S3.** A real MinIO PUT is acknowledged, then the fixture cuts the verification connection and introduces a newer foreign version at the same key. The primary failure remains `S3_REQUEST_FAILED`; cleanup removes the originally acknowledged version. Independent version listing and reads verify that the foreign version and unrelated control survive. The separate loopback HTTP test still covers an acknowledged DELETE followed by a visible object and expects `S3_CLEANUP_NOT_CONFIRMED`. [Native fault fixture](../../scripts/ci/s3-outage-fixture.py) · [Independent state assertions](../../scripts/ci/verify-native-datastores.sh) · [HTTP fixture tests](../../src/test/java/com/specdriven/regression/contract/v03/adapter/S3V03AdapterTest.java)

### HTTP request journal fixture

For `http_mock.v0.3/verify_requests`, `mock.request_filter_ref` references a fixture with exactly two fields, for example `{"method":"POST","url":"/payments"}`. Both must match the recorded request. The expected count defaults to one and may be zero. An optional `mock.body_pattern_ref` filters by exact JSON value. The journal evidence records the expected and observed counts.
